# Spec design template — FinOps angle, evidence check (Sept 2026)

Question asked: does the newly-adopted `spec_design_template.md` (EARS behaviors + RFC 2119 constraints, stable IDs) hold up as a *cost* lever, not just a quality one — i.e. is "assistant reading well-defined specs → better quality / less spend" backed by anything, or is it an assumption worth stating plainly and moving past? Checked against literature the same way the rest of this project's FinOps work has: primary sources where possible, evidence graded, gaps stated rather than papered over.

## Bottom line

The causal chain the template rests on — **ambiguous input → wrong/rejected output → rework → more tokens spent** — is real and quantified, but only at the *first link*. Nobody has measured the second link (rework → token cost) for coding agents specifically; it's argued everywhere in 2026 commentary and measured nowhere found. So the template is well-justified on quality grounds (this is what the template's own rationale already claims, correctly) and only *inferred*, not measured, on cost grounds. That inference is reasonable and worth stating as such — not worth overclaiming.

Three evidence tiers, same discipline as the rest of this project:

## Tier 1 — validated on real systems (the strongest link)

**Requirement ambiguity measurably degrades LLM code-generation correctness, with real numbers, across multiple models.**

- **Orchid benchmark** (arXiv, function-level code gen on HumanEval+/BigCodeBench, 1,304 tasks / 5,216 ambiguous variants, 246 person-hours of human curation): introducing four categories of linguistic ambiguity (lexical, syntactic, semantic, vagueness) into otherwise-identical requirements dropped Pass@1 by an average of **7.22 percentage points (16.25% relative)** across models, with GPT-4 losing up to **31 points** on some ambiguity types and Claude 3.5 up to **31.1 points** on syntactic ambiguity specifically. Conflict rate between repeated generations on the same ambiguous requirement roughly doubled (e.g. GPT-4: 14.09% → 28.29%). Models are bad at self-detecting the ambiguity that hurts them: ~50% precision, <23% localization rate. [Assessing the Impact of Requirement Ambiguity on LLM-based Function-Level Code Generation](https://arxiv.org/html/2604.21505v1)
- **ClarifyGPT** (FSE 2024 / ACM, peer-reviewed): a clarification step before generation (detect ambiguity → ask clarifying question → regenerate) raised Pass@1 by **+7.7 to +9.8 percentage points** across GPT-4 and ChatGPT on four benchmarks. This is the inverse experiment — confirms the same effect from the recovery side. Notably, the paper does **not** report the token/API overhead of the clarification step itself, so the net cost tradeoff (extra clarification tokens vs. saved regeneration tokens) isn't in the primary source. [ClarifyGPT (arXiv)](https://arxiv.org/abs/2310.10996) · [ACM version](https://dl.acm.org/doi/10.1145/3660810)
- **Structured-prompt comparison study** (arXiv, controlled, small-n but directly on point): a checklist-structured prompt vs. an equivalent raw/vague prompt scored **7.50/8 vs 5.67/8** on a quality rubric (+32%) while using **29% fewer tokens** (683 vs 962 mean tokens) to reach an accepted answer in a single turn. A clarifying-question condition (model asks back) actually used *more* interaction effort (1.96 turns) for a *worse* quality score than the checklist condition — i.e., front-loading structure beat back-and-forth clarification on both axes in this study. [Less Back-and-Forth: A Comparative Study of Structured Prompting](https://arxiv.org/html/2605.20149v1)

**Read together:** ambiguity costs measurable quality (Orchid), removing it after the fact recovers most of that quality (ClarifyGPT), and providing structure *up front* is more token-efficient than removing ambiguity conversationally after the fact (structured-prompting study). That last point is the strongest direct support for a spec-first workflow specifically, not just "specs are good" in the abstract — the template's whole bet is to pay the structure cost once, at spec time, rather than repeatedly, at generation time.

## Tier 2 — prescriptive but not independently evidenced (the template's own precedents)

- **EARS itself has no quantified validation, including in its own primary source.** The official EARS guide (Mavin) makes qualitative claims only ("reduces or even eliminates common problems") with no defect-rate, ambiguity-rate, or effort numbers from the original Rolls-Royce work or since. [alistairmavin.com/ears](https://alistairmavin.com/ears/)
- A 2025 peer-reviewed empirical study of EARS in PLC (industrial control) requirements engineering measured testing mechanics (test-case count, coverage) but explicitly did **not** quantify ambiguity or defect rates versus non-EARS requirements, and flagged completeness (not ambiguity) as the most common issue encountered. [SN Computer Science, 2025](https://link.springer.com/article/10.1007/s42979-025-03843-3)
- **RFC 2119 has zero empirical ambiguity/clarity studies** — every hit is about the keyword-casing errata (RFC 8174) or ESL-engineer usage guidance, not about measured effect on requirement quality. It's adopted purely as a vocabulary convention, same as this project's template treats it.
- **Industry "spec-driven development" commentary in 2026 argues the causal chain to agent token cost directly, but every piece checked (O'Reilly, arXiv SDD position paper, the "U-shaped cost curve" post, the EARS-for-agents Medium piece) is argumentative, not measured.** The SDD arXiv paper's own line is representative: *"Empirical studies…though nascent, suggest…"* — citing a "50% error reduction" figure with no traceable source. This is the same "saturated, shallow, look-alike" pattern already flagged in `finops-agentic-shift-left-brief.md` for the broader FinOps-for-AI genre. None of these pieces would survive this project's citation bar on their own.

## Tier 3 — not found

- No study quantifying rework's token/cost multiplier **for coding agents specifically** driven by spec/requirement ambiguity (as opposed to code-gen Pass@1, which Tier 1 covers). The closest attempt found (a retry-failure-rate cost post) explicitly disclaims its own numbers as "general observations" and "constructed examples," not measurements — it says outright "always measure with your own workload."
- No study isolating EARS format specifically (vs. plain structured prose, vs. Given/When/Then, vs. checklists) as the best structure for agent consumption. The structured-prompting study (Tier 1) used a generic checklist, not EARS — the format-specific claim in the template's rationale ("EARS is what agent-spec tools converge on") is an adoption/convergence observation (Kiro, Spec Kit — verified real, both do use EARS-shaped acceptance criteria), not a comparative performance claim.

## What this means for the template

Nothing here says the template is wrong — it says precisely what tier its own justification sits at, which is more honest than most of what's published on this topic in 2026:

1. **Keep the EARS/RFC 2119 choice, but the "why" section should say what's actually verified**: EARS is the de facto convergence format for agent-spec tools (true, adoption fact) and structure-over-ambiguity is quality-and-efficiency-validated in general (Tier 1, but via a generic checklist study, not EARS specifically) — not "EARS is proven to cut agent costs" (unverified, no such study exists).
2. **The FinOps angle earns its place as an explicit, labeled inference, not a proven claim**: "a spec with unambiguous BHV-*/CON-* rows removes the ambiguity that Tier-1 research shows degrades Pass@1 and drives conflicting/rejected generations — and doing that once at spec time is shown (structured-prompting study) to cost fewer tokens than resolving the same ambiguity conversationally during generation." That's a defensible, evidence-chained claim. "This will cut your token spend by X%" is not — no study measures X for this exact chain.
3. **One template addition earns its place given the evidence, at negligible cost**: a **Testability check** on each `BHV-*` row — can this row's SHALL be verified by a single, unambiguous test? — is the cheapest way to catch the completeness/vagueness gap that both the EARS empirical study (completeness was the #1 issue encountered) and the Orchid taxonomy (vagueness as its own ambiguity category) independently flag as the residual risk EARS's fixed sentence shapes don't fully close by themselves.
4. **Track it like the rest of this project does**: since the user is already logging tokens per session per ticket, the Stage-A spec tickets (#31–#35) are a real, cheap opportunity to observe (not assume) whether specs written to this template correlate with fewer follow-up/rework sessions on the implementation ticket that consumes them — turning tier-3 ("not found in literature") into this project's own tier-1 evidence, specific to this codebase, the same way the two self-correction events already logged in `finops-shift-left-slide-content.md` point 6 became this project's own proof-by-iteration.
