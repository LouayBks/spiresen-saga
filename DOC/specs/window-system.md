# Spec: Window system (morph-open, breadcrumb, fullview, recursive canvas) (#44)

Format per `DOC/templates/spec_design_template.md` (ADR-006). Formalizes `boxes-plan.md` §9 into BHV-*/CON-*.

**Revision note (2026-09-18, part 1):** the first draft of this spec assumed a group node's window shows flattened, no-id "inline children" (per `application_architecture.md`'s then-current "group-nesting exception") and spent most of its content managing the consequences of that: an auto-scatter layout with no real meaning, a fake-structure risk, and a depth cap to bound it. That underlying model was wrong — corrected in `application_architecture.md` (2026-09-18): a node with children contains a real **nested Map** (its own id doubles as the Map partition key), using the exact same Node/Link/View system as the top level. This draft removes everything that only existed to manage the old model's fake-structure problem, because that problem no longer exists — a nested Map's contents are real Nodes the owner drags and links exactly like the top-level canvas, not an algorithm's guess at where they should sit.

**Revision note (2026-09-18, part 2):** `kind` (including "group") is retired as a stored field (`naming.md`, `content-authoring.md`). Every "group-kind Node" reference below means, precisely: a node with 2+ children, per `content-authoring.md` CON-8's inference order. This revision also adds the grid-vs-freeform layout rule for a nested Map's *default* arrangement, settled in discussion after the first draft.

**Revision note (2026-09-18, part 3): at most one window is open at a time, for now.** Withdraws §9's original window-*stack* model (a new window opens on top of an existing one, the parent auto-fullviews as a backdrop, closing the child reverses it). Instead: exactly one window exists once you've clicked into anything. Navigating deeper (clicking a node inside the open window) or shallower (clicking an earlier breadcrumb segment) **replaces that same window's content** and grows or shrinks the breadcrumb — it never opens a second simultaneous window. The owner can still manually expand the single open window to fullview at any point ("becoming the map" — edge-to-edge, indistinguishable from the outer canvas — while the breadcrumb stays visible so it's clear you're still inside a nested Map, not back at the top). Explicitly scoped "for now" — multi-window stacking isn't rejected forever, just out of scope until there's a real reason to bring it back.

**Revision note (2026-09-18, part 4): window chrome state (windowed vs. fullview, and rect) persists like a desktop OS window, not per-node.** Confirmed in discussion: (1) a nested Map still gets its own ≤3 Views per `alternate-views.md` — what "resolves the parent" so navigation never gets lost is the breadcrumb chain of Node/Map ids, not View state, which each Map resolves independently; (2) fullview persists through navigation, forward or backward, until the owner manually restores it — it is **not** tied to any particular breadcrumb level; (3) windowed-mode size/position is remembered the same way, Windows/macOS-style: maximize once, and the *next* window you open (even for a different node, even in a later session) opens already maximized; resize it while windowed, and that becomes the remembered rect for next time. Stored client-side (`localStorage`, a "the visitor's own browser" preference, not server-side content) — defaults to windowed, at `boxes-plan.md`'s existing default rect, with nothing stored yet.

**Revision note (2026-09-19): layout mode is derived per View and reversible — the one-way grid→freeform switch is withdrawn.** Decided during the #36 data-model discussion, superseding part 2's rule and CON-6/BHV-12 as originally written. A View's layout is a pure function of whether that View has any Link: **no Links → grid, at least one Link → freeform**, evaluated per View (not per Map — Links are View-scoped by `alternate-views.md` CON-3, so a Map can have one freeform View and one grid View at the same time). Because it is derived, nothing about it is stored, and deleting a View's last Link returns that View to grid. Consequences: (1) a top-level Map is freeform from its first render only because it is provisioned with a Link (`accounts-and-auth.md`), not because of any special case; (2) nodes carry `{w, h}` size in grid units instead of a tier (`box-sizing.md`), so "block span per tier" stops being an open question; (3) on reverting to grid, stored freeform positions are never overwritten — the grid arrangement is computed at render time, so re-adding a Link restores the original freeform layout.

## Objective

Formalize the window/expansion mechanism — the thing that makes "nodes within nodes" actually buildable and navigable, and the direct answer to whether the app's recursion is covered by a spec anywhere.

## Context

- Ticket: #44.
- Updates once accepted: `boxes-plan.md` §9 only if a real gap is found (none expected — this is a formalization pass, not a redesign).
- Cites, doesn't redecide: `node-link-lifecycle.md` (Node/Link creation, drag, deletion — applies unchanged inside a nested Map), `alternate-views.md` (a nested Map gets the same ≤3-View system as any Map), `box-sizing.md` (node size — explicitly does not apply to window rects, see CON-1), `content-authoring.md` (article/gallery *authoring*; this spec owns *reading* an already-authored one — content-authoring.md's 2026-09-18 revision drops video as a hosted type entirely, see BHV-9 below).

## Decisions

- **A window's rect is independently resizable — not governed by `box-sizing.md`'s node size.** A Node's `{w, h}` size is its footprint *on the canvas*, in grid units; the window that opens when you click it is a separate UI surface with its own free-resize rect in pixels (min-size floor only). Different object, different unit, different purpose.
- **A node with children opens a window showing a real nested Map, not a rendering of summary data.** Opening it runs one `Query` on `PK: MAP#{thatNodeId}` (per `application_architecture.md`'s correction) and gets back real Node/Link rows — the same shape a top-level Map's canvas gets. Dragging a Node inside that window *is* `node-link-lifecycle.md`'s existing drag/position behavior; drawing a link between two of them *is* its existing drag-to-link flow. Nothing new is invented here — this spec's only job is confirming those rules apply unchanged one (or more) levels down.
- **Layout is derived per View: no Links → grid, at least one Link → freeform (2026-09-19 revision — replaces the earlier one-way switch).** A View with no Links arranges its Nodes in a fixed grid, Android-homescreen-widget style: each Node occupies a `w × h` block of cells, per its own size (`box-sizing.md`). As soon as the View has at least one Link it is freeform — Nodes go wherever they're dropped, the same as the outer canvas. Deleting the View's last Link returns it to grid, with stored freeform positions preserved untouched (the grid arrangement is computed at render time, not written back) so the freeform layout reappears if a Link is added again. This still replaces the withdrawn auto-scatter/depth-cap machinery from the first draft: a grid with no Links doesn't pretend to carry meaning, and freeform only applies once the owner has composed real relationships.
- **A nested Map gets the same ≤3-View system as any Map.** `alternate-views.md`'s rules (1–3 Views, per-View positions, View-scoped Links) are written generically ("a Map," never "the top-level Map") — they already apply here without modification. A window for a deeply-nested group can have its own alternate arrangements exactly like the outer canvas can.
- **No depth cap.** The earlier cap existed only to bound the old model's fake-auto-layout problem, which doesn't exist anymore — a nested Map is fetched lazily (one `Query` per level, only when opened), so depth doesn't multiply cost the way embedding everything upfront would have. This matches `boxes-plan.md` §9 as literally written: depth is allowed, and the breadcrumb is the tool that keeps it legible (per the single-window revision below), not a limit on how deep an owner can nest.
- **Everything else in §9 is confirmed as written, not redecided, with two adjustments**: morph-open via FLIP from the clicked element's exact rect (now: morphs the one existing window's content, not a new DOM window, when navigating deeper); fullview as a single state, now reached only manually (the automatic on-stack trigger no longer applies — there's nothing to stack); breadcrumb-not-back-button navigation (now: the breadcrumb drives the single window's content, not which windows are open/closed); article leaves open as a document view; the "opener" convention for click targets inside draggable regions. **The second adjustment: "video leaves open as a player-frame view" is withdrawn** — `content-authoring.md`'s 2026-09-18 revision drops hosted video entirely (cost-driven); a gallery leaf opens as a lightbox/carousel view instead (BHV-9), and a video *link* (e.g. YouTube, with its oEmbed thumbnail per `content-authoring.md`) renders inline wherever links render, it doesn't open its own window.

## Constraints (`CON-*`)

| ID | Statement | Notes |
|---|---|---|
| CON-1 | A window's rect (position/size) MUST be independently resizable and MUST NOT be constrained to `box-sizing.md`'s grid-unit node size. | Different object (window vs. Node footprint), different unit, different rule. |
| CON-2 | Fullview MUST be a single visual/interaction state, reached only via the manual maximize control — there MUST NOT be a distinct "automatically fullviewed" appearance. | Simplified now that stacking (the old automatic trigger) is withdrawn — see CON-7. |
| CON-3 | A node-with-children's contents MUST be real Node/Link/View rows, addressable and authorizable exactly like a top-level Map's — MUST NOT be flattened into non-addressable summary data. | Reverses the withdrawn CON-4 from the first draft; restates `application_architecture.md`'s correction in this spec's own terms. |
| CON-4 | A node's own id MUST double as its nested Map's partition key (`PK: MAP#{nodeId}`) once it has children — MUST NOT require a separate stored reference to find it. | |
| CON-5 | Every draggable region's pointer-capture handler MUST exempt any descendant explicitly tagged as an opener, rather than relying on a per-button ad hoc check. | |
| CON-6 | A View's layout mode MUST be derived solely from whether that View has at least one Link (none → grid, some → freeform) — MUST NOT be a stored flag, MUST NOT depend on any other View's Links, and switching it MUST NOT rewrite stored positions. | Replaces the withdrawn one-way-switch rule (2026-09-19). |
| CON-7 | At most one window MUST be open at a time — navigating into a deeper node or an earlier breadcrumb segment MUST replace the currently-open window's content, MUST NOT open an additional simultaneous window. | The core rule of this revision. Stated as "for now" in Decisions — a deliberate scope limit, not a permanent rejection of multi-window stacking. |
| CON-8 | The window's mode (windowed/fullview) and rect MUST be a single persistent client-side preference — MUST NOT reset on content navigation (forward or backward), MUST NOT reset when a new window is opened later, and MUST NOT be tied to any specific Node/Map. | Windows/macOS-style window memory, per Decisions part 4. Governs BHV-1's destination rect and BHV-2/BHV-4's "unchanged" requirement. |
| CON-9 | A Map's active View MUST be resolved independently at each breadcrumb level — navigating away and back MUST NOT reset it to a default or inherit the parent level's active View. | Answers "how do we not get lost": the breadcrumb (Node/Map id chain) resolves ancestry; View state is separate and per-Map. |

## Open questions

- **#40's scope needs widening.** It was written assuming View-switching UI exists only on the outer canvas; per this spec's Decisions, a nested Map can have its own Views too (resolved independently per CON-9), so the switching UI needs to exist inside the window as well. Not resolved here — flagging for whoever picks up #40.
- **Grid mechanics still undefined.** Node size is now a free `w × h` in grid units (`box-sizing.md`), so block spans are no longer an open question — what remains: the grid's column count and how a Node wider than it behaves; how overlapping blocks are resolved when the grid is computed at render time (including when reverting from freeform, where stored positions may overlap or be fractional); and whether the owner can drag-rearrange within grid layout, and if so where that arrangement is stored (the current assumption — stored positions are only overwritten by an explicit drag — is not settled). Needs its own design pass, not decided here.

## Out of scope

No implementation (that's #38). Exact FLIP animation timing/easing, breadcrumb truncation behavior at very deep paths, and document/player-view visual styling are implementation details, not modeling decisions.
